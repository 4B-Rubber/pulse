## Finding 1 — P1：静默卸载不等于升级卸载

PR #8，installer/PulseSetup.iss:380-384（PR head 行号）。

新补丁通过 `if not UninstallSilent` 包裹 Run 值和 Directory/Drive 打开关联清理。任何真正的静默卸载也会跳过清理。用户在应用中开启过相关偏好后，通过静默卸载命令移除 Pulse，可能留下指向已删除 pulse.exe 的文件夹/磁盘默认打开命令，导致正常打开目录受影响；应用后写入且未受安装日志管理的自启动值同样可能残留。

建议：用明确的升级参数/握手区分升级与真实卸载，不按是否显示 UI 判断。真实卸载无论静默或交互都清理属于当前安装的关联。升级方备份并恢复实际状态，还需考虑失败回退。

补充检查：同文件第 97 行仍有 `[Registry] ... Flags: uninsdeletevalue`。对于安装任务创建的启动值，跳过 usPostUninstall 的显式删除不等于阻止安装日志执行删除；新安装是否重建又依赖 startup 任务选择。此外首次升级调用的是旧版本卸载器，新版本脚本不能改变已经安装的旧卸载器。应验证完整升级链，不能仅凭这 15 行判定偏好保留问题解决。

建议定向验收：真实静默卸载；旧版升级到新版；安装任务与应用内偏好不一致；升级取消/失败；自定义安装目录。不要在用户现有安装上直接试验。

## Finding 2 — P1：预览冷却标记可能记到新选中文件，而非卡住的处理器

PR #10，src/ui/preview_handler_host.cpp:793-795；关联 735-747、769-780（PR head 行号）。

`RetireStalledApartment` 使用 `ExtensionOf(last_path_)` 调用 `NoteStalledProvider`，而 `last_path_` 在每次发布新选择时立即更新，并不代表当前 STA 实际卡住的文件。

触发路径（静态推导，未实机复现）：

1. 开始打开 A.pdf，处理器持续阻塞。
2. 在 3 秒 superseded 超时之前切换到 B.docx；Sync 尚不回收 worker，先将 last_path_ 改为 B.docx，并排队 B。
3. 后续超时仍卡在 A.pdf，却将 .docx 标为冷却。
4. 健康的 Word 预览被至少约两分钟的冷却排除，真正卡住的 PDF 类型未被标记，再次访问仍可能重试该问题处理器。

建议：在 worker 开始实际处理时保存受锁保护的路径/扩展名或处理器 CLSID，超时从该快照取归因；区分“正在打开的请求”与“最新排队的请求”。不要从 UI 的最后选择推导实际卡住的 provider。

建议新增最小测试：A 类型注入阻塞，在超时前切到不同类型 B；触发回收后断言 A 冷却，B 可立即创建新 apartment。不只测试同扩展名快速切换。
