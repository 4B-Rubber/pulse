## 与上一轮比较的边界

参照 docs/mcp-index-cpu-background.md：旧服务工作集为 330–335 MiB，本轮约 188–197 MiB；结束值 333.41 → 196.50 MiB，现场读数低约 137 MiB。

但旧服务在当时观测开始前已运行约 17 分钟，新服务在本轮观测开始前仅运行约 2.5 分钟，进程重启后的缓存热度、映射页驻留和后台事件负载不同。因此不能把这 137 MiB 全部归因于代码优化，也不能据此保证长时间运行仍停留在约 196 MiB。

CPU 也不是全面下降：旧索引服务/主程序/网络代理平均分别为 0.0536% / 0.1099% / 0.3213%，本轮为 0.0646% / 0.3638% / 0.6658%；三者合计从约 0.485% 到 1.094%。这不是受控 A/B，不能直接判定版本回归；不过必须如实记录，而不是只报告内存下降。本轮未复现索引服务持续高 CPU，但主程序偶发活动与网络代理后台负载仍值得后续关注。

## 结论与下一步

新包确已安装，隐藏驻留场景下索引服务 CPU 仍低，当前工作集低于上一轮；主程序和网络代理的私有提交较平稳。服务私有提交仍有净增长，需要更长、接近相同进程运行时长的观察确认是否趋稳。

本次 15 秒采样不能捕获几十毫秒的落盘临时峰值，也未主动触发冷摘要，因此既不能替代此前微基准，也不能声称验证了实机查询加速。若继续验证，优先让当前进程保持运行 15–30 分钟后复测，再单独测量用户正常查询时的响应和更细粒度内存峰值；不要通过重启、丢弃索引或工作集裁剪影响比较。
