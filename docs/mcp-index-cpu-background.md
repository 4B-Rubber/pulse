# Pulse 隐藏驻留后的 CPU 复测

日期：2026-09-18。前一轮主程序退出场景见 docs/mcp-index-cpu-postinstall.md；修复说明见 docs/mcp-index-background-cpu.md。

## 场景与方法

- 本机 15:41:08 至 15:44:13，12 个约 15 秒区间，有效观测时长 184.783 秒。
- pulse.exe PID 23900 全程存在；通过只读 EnumWindows / IsWindowVisible / IsIconic 核验，PulseMainWindow 在所有窗口采样中 visible=false、minimized=true。因此此次覆盖主程序隐藏/最小化驻留，而非完全退出。
- 服务 PID 27152、网络代理 PID 11304 均与上一轮相同，没有在两次观测之间重启这两个进程。
- 已安装 pulse.exe 与 Pulse.Index.exe 的 SHA-256 均匹配此次构建，版本仍为 1.0.32。
- CPU 使用 Win32_Process 累计用户态和内核态 CPU 时间差，按 6 个逻辑处理器归一化为整机百分比。峰值指约 15 秒区间平均，不是瞬时值。
- 全程只读观察，没有改变窗口状态、用户设置、服务状态或程序文件，没有启动构建或功能测试。
- 原始数据保存在本机临时目录 pulse-cpu-background-observation-20260918-9288.json；窗口状态同时记录在命令输出中。

| --- | ---: | ---: | ---: | ---: | --- |

三个进程平均合计约 0.485% 整机 CPU。主程序工作集在前约一分钟增加后保持约 114 MiB，服务工作集在约 330–335 MiB 范围内波动。工作集不等同于私有提交，不能仅凭三分钟变化判定或排除泄漏。

服务阶段日志覆盖约 180.77 秒：应用变化 9608 次，增量落盘阶段 11 次，事件唤醒 8141 次；没有新增 merge、rebuild 或 recovery 调用，各阶段错误计数没有增加。merge 的最后原因仍为 fragmentation，但本轮调用增量为 0，不能把历史最后原因当作本轮正在执行合并。

## 判断

- 本轮后台驻留场景没有复现最初持续高 CPU，索引服务平均约 0.05%，与前一轮主程序退出时的 0.07% 同属低占用范围。
- 主程序确实仍在运行且主窗口不可见，补上了上一轮缺失的驻留场景验证；结果支持本次修复在当前场景下没有继续产生先前的持续 CPU 负载。
- 服务工作集明显高于上一轮结束时的 71 MiB，但本轮处于约 330–335 MiB；无法仅凭这些样本确定增加由哪类缓存、映射页或历史数据造成。不宣称内存优化已经完成。
- 结论仅覆盖当前约三分钟的后台驻留状态，不承诺前台搜索、长时间运行或其他工作负载下均无性能问题。
