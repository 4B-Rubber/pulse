# 增量名字池局部整理与合并诊断

日期：2026-09-18。

## 结论与执行边界

已完成一轮定向修复和相关验证：名字垃圾不再直接请求全量 MergeBase，改为只整理堆上的增量名字池；必要全量合并条件继续保留。新增诊断用于后续区分实际合并原因、间隔、耗时及整理容量。

本轮保留了任务开始时已有的未提交修改，仅补丁修改相关索引代码、诊断和定向测试。没有安装、替换运行中的程序、重启服务、修改设置或裁剪工作集；没有运行全面回归。当前安装版本仍不能视为已经包含本次修复。

本报告承接 docs/mcp-index-memory3-retention.md 与 docs/mcp-index-memory3-retention-review.md。既有三次 fragmentation 合并的具体子条件仍不能追溯确认；本轮消除的是已核实的代码路径，并非声称已证明那三次全部由名字垃圾触发。

## 核验发现

- 原维护逻辑将删除比例、约 2 MiB 名字垃圾、相对基表名字池的垃圾比例三个条件 OR 在一起，统一请求全量合并。
- 原垃圾计费覆盖普通堆节点改名，但未完整覆盖映射基表节点的重复 patch 改名，以及 delta 重放的 patch 替换。
- 堆名字偏移有两类所有者：live_.nodes 与 patches_ 中的 has_name 项。重放可能同时保留某个堆节点的原始名字与覆盖它的 patch 名字，不能只遍历当前 NameOf 可见的内容。
- child_map_ 保存哈希和节点编号，不保存名字指针；查询在引擎锁下读取名字。局部整理无需重编号、换代或重新构建查询索引。

## 实施内容

### 局部整理与安全边界

新增 src/index/index_name_pool.h，统一预检所有堆名字引用及总长度，先完成新池分配，再进行不会分配的复制、偏移更新和 swap。无效引用、偏移范围溢出或分配失败返回错误；预检或分配失败时旧池和偏移不变。

保留包括 tombstone、被重放 patch 遮盖的节点在内的所有原始引用，只释放没有引用的字节。保留节点 ID、父子关系、FRN、属性、查询代际、feed 游标、历史路径和 USN 游标，不搬移映射基表名字。该策略有意保守，不试图在本轮回收仍有原始引用但当前不可见的名字。

整理阈值为：已计费垃圾至少 1,048,576 个 UTF-16 字符（Windows 上约 2 MiB），且至少占当前增量池逻辑长度的 25%。每次尝试后至少等待 60 秒，包括失败。比例门槛用于避免为很少的垃圾重复复制很大的有效增量池，不再依赖映射基表的名字池大小。

在工作线程独占引擎锁下整理；若本轮已选中必要全量合并，则不先做重复的局部整理。整理失败不会因此回退到立即全量合并。

### 必要合并与计费

- 保留删除比例超过 10%、结构变化阈值、delta 大小阈值、安静期发布以及显式强制合并。
- 保留全量合并失败退避及原有正常间隔机制。
- 删除比例的原因由泛化 fragmentation 改为 deleted_ratio。
- 补齐 USN、目录通知及 delta 重放路径中的旧 patch 名字计费；原堆节点改名计费保留。
- 未进行全量 FlattenLocked 的 reserve/流式构建改造，必要合并的完整副本及其峰值问题并未在本轮消除。

### 诊断

新增 src/index/index_maintenance_probe.h，通过已有每分钟、轮转限额的 pulse-index-timing.jsonl 输出 maintenance 对象，不记录逐个文件名。

记录全量合并的分类累计次数、最近一次开始时间、距前次成功合并的间隔、耗时、提交结果、节点数、删除数、结构变化量、基表/增量池/垃圾字符量及磁盘 delta 字节数。name_pool 记录尝试、成功、失败、最近一次整理前后长度和 capacity 字节数，以及累计回收字符量。新增 name_pool_compact 阶段提供累计耗时、CPU 时间及错误信息。

这些是累计计数和最近一次快照，不是完整事件流水；合并前后既有内存采样仍不是 FlattenLocked 内部的严格峰值。

### 隔离样本的容量与耗时

样本使用小型合成树和 4,600 次长度为 240 字符的名字替换，随后恢复短名字。两种状态使用同样的改名序列；这里不是百万级生产索引的前后对照实测。

| 状态 | 整理前池 capacity | 整理后池 capacity | 回收字符数 | 包含取锁的单次整理时间 |
|---|---:|---:|---:|---:|
| 纯堆 | 2,932,346 B | 348 B | 1,104,030 | 0.1359 ms |
| 映射基表 + 增量 | 2,253,828 B | 66 B | 1,104,018 | 0.1278 ms |

两个样本的局部整理均未调用全量合并或 MergeFlattened 采样。capacity 下降是该容器容量实测，不等于进程私有提交同步下降，也不能据此宣称生产机已节省约 285 MiB。耗时是一次小型样本结果，不是分位数、压力测试或生产 SLA。

## 未验证项与下一步

- 没有部署后观测，因此真实合并频率、后台 I/O、查询延迟和进程内存峰值的改善幅度尚未确认。
- 无效引用失败路径已实测；分配失败的无副作用保证来自实现顺序和异常处理检查，本轮没有故意耗尽系统内存或注入 bad_alloc。
- 并发测试是基本正确性检查，不是长时间压力测试；没有新增崩溃恢复故障注入。既有发布流程未改动。
- 主程序/网络代理长期保留内存、网络重扫及约 28 MiB 的全量副本容量余量不在本轮修复范围内。

建议下一步在用户确认部署方式后，仅进行一次正常负载的部署后观察，至少覆盖此前约 15–20 分钟的合并间隔并观察多个维护周期。比较 maintenance 中的真实触发原因、次数、耗时及 name_pool 的回收量，并结合查询体验与进程内存采样。不能只因短时未合并就宣布长期完成，也无需因此扩展成全面泄漏追踪。
