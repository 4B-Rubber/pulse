## 结论摘要

1. **合并副本的主要构成已量化**：对既有快照建立的容量模型约 **285.479 MiB**，与之前三次合并展开阶段约 **288–289 MiB** 的全进程私有提交增量接近。还有约 **55.412 MiB** 的遍历数组在 FlattenLocked 内部短时存在，现有展开后采样点并不覆盖这部分存活期。
2. **主程序和代理本轮没有继续增长**：19:24:06–19:26:07 五次快照中，主程序私有提交保持 **165.766 MiB**，代理保持 **62.535 MiB**；按 VirtualQueryEx 分类的 MEM_PRIVATE 已提交区域总量也不变。
3. 代理不是没有工作的空闲进程：配置了 **3 个网络根**，本地分卷共约 **131 万条记录**，正在进行网络目录重扫；两分钟内当前根扫描计数 **176128 → 342016**，私有提交仍持平。
4. 不能据此宣布长期无泄漏：此前主程序增加的约 39.63 MiB 和代理增加的约 17.35 MiB，尚未由活对象计费或分配栈逐项归因。现有证据支持“目前停在较高平台”，不支持继续按一分钟增量外推固定泄漏速率。

## 一、合并副本容量模型

### 数据与验证方法

只读读取此前已发布的聚合快照：

`C:\ProgramData\Pulse\Index\v9\9ACBEFD40DDAC9E8\base-a.bin`

它包含 2908365 个节点、70968232 个 UTF-16 字符、2890167 条文件编号映射、5 卷。单独解读 manifest 得到 generation=150、active slot 为 b；本探针明确针对保留的 a 槽快照，不冒充当前实时 overlay，也不据此推断新发生了几次合并。

| Attr，12 B × 节点数 | 33.284 MiB |

实际探针：`bench_data/merge-capacity-20260918/probe.cpp`、`probe.exe`、`result.txt`。最终编译/运行退出 0，无编译警告；**2 PASS / 0 FAIL**：

- MSVC 范围插入与 pair vector 增长和模型一致。
- 流式累计节点名字长度、逐卷 FRN 数量与文件头一致。

### 为什么现有日志可能漏掉更高的内部瞬间峰值

`index_engine.cpp:2097–2192` 中，FlattenLocked 先创建全节点 remap、子节点统计、邻接数组，然后生成 nodes / attrs / pool 和各卷 frn_build。工作数组在返回时销毁。

`MergeBase` 在 FlattenLocked 返回后才采样 `MergeFlattened`，所以此前记录的约 376 MiB 私有提交不能当作整个函数内部的严格峰值上限。完整 `Store snap` 则一直保留到写聚合索引、提交映射、写分卷、记录合并日志后，函数返回才释放。

## 二、合并触发存在明显的优化目标

`index_engine.cpp:3508–3517` 的 fragmentation 判断是三个 OR 条件：

- 删除节点超过总节点的 10%；
- `pool_waste_ >= 1 << 20`；
- 名字池浪费超过映射基表名字池的 10%。

`pool_waste_` 按 `Node.len` 累加，单位是 UTF-16 字符，因此第二条约为 **2 MiB 名字数据**。一旦成立，现有路径调用全量 MergeBase；非 quiet_changes 原因还会传 `force=true`，绕过普通最短合并间隔检查，但仍保留失败退避。

所以，“约 2 MiB 的增量名字垃圾触发约 285 MiB 的全量副本”是代码中真实存在的路径。此前三次日志均为 fragmentation，但日志没有分别记录 deleted / pool_waste / base_pool，**尚不能断言那三次具体都由第二条触发**。

### 推荐的修复顺序

1. **先做增量名字池的局部整理**：只回收已无引用的名字字节，保留节点 ID、父子关系、FRN、游标、历史及查询语义；不要为小规模名字垃圾立即展开整个基表。删除比例、结构变化、delta 大小等真正需要发布新基表的合并条件继续保留。
2. **必要全量合并再做容量优化**：预计算名字字符总量、预留 FRN 容量，可减少模型中约 28 MiB 的容量余量；但这不会消除最低约 257 MiB 的完整副本内容，也不等价于实机一定节省 28 MiB。
3. 如果仍需显著压低真正合并时的峰值，再评估分卷或流式构建，保留发布原子性、查询代际、崩溃恢复和文件编号映射。这比简单提前 clear 更复杂；snap 在写分卷完成前仍有实际用途。

局部整理实施前仍需验证名字偏移引用、异常安全、并发查询与历史路径不变等边界。本轮只完成定位，没有应用这个方案。

方法：对主程序 PID43336 和代理 PID12920，读取进程指标并用 VirtualQueryEx 查询地址区域的类型/提交大小。没有读取进程内存内容、注入代码、暂停线程或做堆快照；区域枚举也不是原子堆统计。

| 主程序 PrivateMemorySize64 | 165.766 MiB | 165.766 MiB | 全部一致 |

进程私有提交与 MEM_PRIVATE 类型区域求和并非同一口径，不能把两者差额直接当成某个模块的堆占用。区域提交大小不变也不代表已有堆页内所有活对象数量不变，仍可能在已有余量内发生分配/释放。

正常代码路径中，NetworkAgentClient 每秒刷新根信息使用替换而非累积追加；搜索消息处理先 TakeResult 再判断请求是否仍有效。仅凭“有结果 map / 有根列表”不足以认定这部分在泄漏。主程序此前增加的约 39.63 MiB 暂不能准确分配到 UI 缓存、请求对象或其他组件，需要后续分类计费或分配跟踪。

## 四、代理实际工作与保留数据

- UTF-8 配置解析确认 3 个网络根。只读发送 REQ_ROOTS=3 查询状态，没有发送新增、删除、重建或 lease 修改请求。
- 磁盘三个分卷当时分别有 425982 / 590272 / 298391 条记录，合计 **1314645 条**，不保证网络根之间无重叠。文件大小合计约 **340.659 MiB**，不能当作驻留内存。
- 两分钟内根 0 为 building 状态，扫描计数从 176128 到 342016；根 1 / 2 已完成。代理私有提交在这段推进过程中不变。
- NetworkIndex::Shard 使用只读文件映射；ShardBuilder 把记录及名字池流式写临时文件，保存时使用 1 MiB 搬运缓冲，并不是将全部网络路径收集成一个内存大数组。
- 本地网络变更历史文件有 **88453 条记录，33554384 B，接近 32 MiB 上限**。ChangeTracker 按租约加载事件历史，内存还包括记录 vector 和路径分配。这是较高常驻基线的候选组成，但磁盘文件大小不等于活进程堆占用，未将它当作此前增量的已证实原因。
- CrawlLoop 以 5 分钟做周期性全量校验；计时在启动/安排批次时更新，而非全批次结束后。如果一轮扫描超过周期，下一轮可能紧跟着开始。目录变化也会排入重扫，当前状态协议没有重扫原因字段，不能认定本轮扫描只由周期到期触发。

因此，代理的后台 CPU 和基线不能再按“没有网络目录、没有工作”解释。下一阶段如需深入代理，优先增加重扫原因/时长、待遍历目录数量及峰值、历史容量等低频诊断，而不是直接减少历史保留、关闭扫描或凭一个增长区间认定泄漏。
