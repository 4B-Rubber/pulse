# memory3 后续性能投入判断

日期：2026-09-18。

## 范围

仅复核 docs/mcp-index-memory3-retention.md 的证据与建议，并阅读根目录 AGENTS.md；没有重新核验源码、原始探针数据或当前进程状态。本结论是基于报告的优先级判断，不是新一轮性能实测。本次不修改生产代码，不运行构建、测试或进程干预。

## 结论

有必要做有边界的定向优化，但没有必要继续泛化追查所有内存增量。当前最值得投入的是全量合并触发策略；网络重扫取决于实际 CPU、I/O 和体验影响；主程序/代理泄漏追踪暂缓升级。

## 优先级与证据

1. 优先处理合并触发路径。报告说明约 2 MiB 的增量名字垃圾可以触发约 285 MiB 全量副本，且非 quiet_changes 路径可能绕过通常的最短合并间隔。这是值得优化的机制，但未证明此前三次合并均由此触发。先在自然发生的合并中低频记录具体触发条件、pool_waste、基表名字池、删除比例、间隔和耗时；若小规模名字垃圾实际主导，则实现增量名字池局部整理，保留必要全量合并条件。先验证名字偏移引用、异常安全、并发查询和历史语义。
2. 网络代理按症状定向检查。五分钟周期按批次启动计时，长扫描可能导致下一轮紧接启动；这只证明有潜在连续扫描路径，不证明扫描成本异常。仅在持续 CPU、网络/磁盘 I/O、功耗或交互影响明显时，记录重扫原因、整轮耗时、扫描间隔与工作量，覆盖完整扫描周期再判断。
3. 暂缓重型泄漏归因。报告的五次样本中主程序 165.766 MiB、代理 62.535 MiB 均持平，代理扫描也在推进；没有继续按分钟外推泄漏速率的依据。但两分钟平台不能证明长期无泄漏，此前约 39.63 MiB / 17.35 MiB 增量仍未归因。只在同等负载与可比阶段下，多轮完整工作周期结束后的基线持续抬升、超过内存预算或出现实际故障时升级分配栈/活对象跟踪。
4. 容量预留是次级优化。约 28 MiB 是模型余量而非实测可节省值，且不能消除约 257 MiB 的完整内容。约 55 MiB 临时工作数组不在展开后采样点覆盖范围内；不要把既有采样当作严格峰值。只有必要合并仍超出明确峰值预算时，再考虑分卷/流式构建。

## 收口标准

在有代表性的相同负载下，比较合并次数、具体原因、耗时与内存峰值，并验证对应功能语义。消除不必要全量合并、必要合并满足约定资源预算、可比周期基线不再持续抬升且无相关体验问题后停止。报告没有给出产品资源预算或延迟目标，因此不能直接宣布整体性能合格，也不应为解释每一 MiB 无限延长调查。
