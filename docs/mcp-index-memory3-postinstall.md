日期：2026-09-18。用户安装后要求继续跟踪内存。本轮只做版本核验、只读观察和日志分析；没有修改源码、重新构建、安装、重启服务、调整设置或裁剪工作集。

## 结论

**本轮观察到的内存大幅尖峰明显减弱，修复后的 USN 原始队列保持很小。** 尚有历史落盘快照阶段约 33–38 MiB 的短时私有提交增量，以及服务基线的小幅增长。短窗口不能证明长期无泄漏，也不能把新旧差值全部归因于单一修复。

## USN 原始队列：现在确实很小

- 当前诊断有 **5 条 USN 流**。
- 前 7 帧采样时当前包数、有效字节、容量、计费字节均为 0；最后一帧有 **1 包，88 B 有效内容 / 88 B capacity / 120 B 计费量**。
- 最后一帧，各存活流生命周期峰值的 capacity 之和为 **17936 B（17.52 KiB）**；计费量峰值之和为 **19688 B（19.23 KiB）**。
- 计费量包含实际 vector capacity 与节点对象，不含分配器内部记账。峰值之和不是同一时刻的全局峰值；流重建后旧峰值不会继续计入。
- 这些值不包含读取缓冲。5 条活跃读取线程对应约 **1.25 MiB** 可复用 I/O 缓冲，另有线程/对象等开销。
- 各帧 `usn_queue_overflows=0`；阶段日志的错误增量均为 0，merge / rebuild / recovery 均没有新增调用，当前服务启动后的这些调用数也均为 0。

因此，在这段实际工作负载下，原始队列的保留容量已经不再是几十至几百 MiB 的量级。它与此前确认的容量放大修复吻合，但旧版没有对应队列统计，不能反推每次旧尖峰具体有多少字节来自队列。

## 基线增长及后续边界

服务私有提交首末约增加 **7.11 MiB**。同期相邻分钟边界的 feed 从 **13552 条 / 3.625 MiB** 增至 **28937 条 / 7.500 MiB**，页容量增加 **3.875 MiB**；overlay 节点 **3362 → 5883**、patch **1661 → 2523**。这些保留结构的增长与基线抬升相符，但统计时刻不完全相同，也没有对所有分配逐项计费，不能把剩余差额武断命名为泄漏。

映射文件长度约为总表 655.18 MiB、分卷 654.26 MiB，不代表这些字节均驻留 RAM。此次没有合并，亦没有验证更长期的 feed 保留上限、换代和合并后的内存平台。

建议继续正常使用，下一阶段观察 30–60 分钟或一次自然合并/换代后基线是否回稳。如需继续压低短时峰值，可再评估历史快照的复制策略，但不应通过缩短历史保留或强制裁剪工作集掩盖问题。本轮未做新的功能改动，观察程序已结束，没有留下持续后台采样任务。
